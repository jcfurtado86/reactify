----------------------------------------
 Esse curso faz parte do projeto de extensão Transferência de Conhecimento de Métodos Ágeis para a Elicitação e Especificação de Requisitos de Software, financiado pela Pró-Reitoria de Extensão da UFPA por meio do edital Navega Saberes de 2023. No módulo anterior, nós vimos um breve nivelamento de conceitos que são importantes para o desenvolvimento do nosso curso. Entre esses conceitos estava o de Engenharia de Requisitos Ágil, que basicamente é a aplicação dos valores e princípios do Manifesto Ágil para as atividades da Engenharia de Requisitos. Uma ideia bastante simples de ser entendida. Contudo, existe um problema por trás disso. A falta de métodos ágeis específicos que busquem apoiar aquelas atividades que compõem a Engenharia de Requisitos, buscando suportar. Para recuperar então essa lacuna, foram propostos dois métodos ágeis para as atividades de Engenharia de Requisitos, que são os métodos REACT e REACT-M. REACT é a sigla em inglês para Requirements Evolution in Agile Context, que pode ser entendido como evolução de requisitos em um contexto ágil. Ele é uma proposta de método ágil para o desenvolvimento de requisitos de software. Esta abordagem tem como objetivo evoluir a linguagem de software, e também a linguagem de software. Esta abordagem tem como objetivo evoluir a linguagem de software. Ela é uma abordagem que permite a evolução de as expectativas e as necessidades de negócio dos clientes ao longo do desenvolvimento de um produto de software. Esse método é composto por cinco cerimônias, que são a Inception, a Story Discovery, Refine, Modeling e Inspection. A Inception é uma cerimônia utilizada para estabelecer a ideia geral do sistema que pretendemos desenvolver. Na Story Discovery, nós começamos a levantar quais são os requisitos desse produto que será desenvolvido. Na cerimônia do Refine, nós começamos a refinar um pouco mais esses requisitos que foram encontrados. Na cerimônia de Modeling, nós estabelecemos a organização e a estruturação desses requisitos. E por último, nós temos a Inspection. Contudo, a Inspection deve ocorrer durante todo o ciclo de vida do React. E por ela, nós temos a atribuição de verificar e validar esses requisitos que estão sendo produzidos nas outras cerimônias. Existem quatro papéis principais no React, que são o de Customer, Existem quatro papéis principais no React, que são o de Customer, Domain Expert, O papel do Team e o Facilitator. Customer é o cliente. Domain Expert é alguém que tem grande conhecimento na área de atuação daquele cliente. Team é o corpo técnico do projeto. O Facilitator é um especialista no React que vai ajudar os demais atores a utilizá-lo durante a atividade de levantamento de requisitos. Os artefatos produzidos durante o React são Product Covers, User Stories, System Stories, UI Storyboards. E nós vamos ver detalhadamente cada um deles no momento certo. Voltando no módulo anterior, nós vimos que a engenharia de requisitos pode ser vista como dois grandes grupos. O grupo de desenvolvimento de requisitos e de gerenciamento de requisitos. O React então busca apoiar as atividades de desenvolvimento de requisitos. Ou seja, a elicitação, a análise, especificação e validação de requisitos. Ou seja, com o React, apesar de ser um grupo de atividades de desenvolvimento de requisitos, falta meios para realizar a gestão da mudança dos requisitos, que inclui a rastreabilidade desses requisitos. E assim surge o React-M. O React-M então é uma proposta de ampliação do React para as atividades de gerência de requisitos. Assim, com a utilização do React-M, nós conseguimos fazer a rastreabilidade e a gestão de mudança dos requisitos durante o projeto. Com a utilização do React, nós temos a inserção de algumas atividades a mais durante o ciclo de vida do React. E alguns novos artefatos também serão produzidos com a utilização do React-M. Em síntese, a utilização do React com o React-M nos apoia a realizar todas as atividades da engenharia de requisitos. Como conclusão desse módulo, nós temos que o React e o React-M são métodos ágeis distintos. Mas eles se complementam para abranger todo o ciclo de vida da engenharia de requisitos.
