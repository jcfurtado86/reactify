Título: MÓDULO 6 - Métodos Ágeis para o Desenvolvimento e o Gerenciamento de Requisitos de Software
----------------------------------------
 Esse curso faz parte do projeto de extensão Transferência de Conhecimento de Métodos Ágeis para a Elicitação e Especificação de Requisitos de Software, financiado pela Pró-Reitoria de Extensão da UFPA por meio do edital Navega Saberis de 2023. Nos dois módulos anteriores, nós aprendemos a elicitar, refinar e validar requisitos usando o React e o React-M. Agora, nós veremos como modelar esses requisitos em três níveis usando a modeling, a quinta cerimônia do React. Este módulo está estruturado em visão geral, modelagem funcional, modelagem de interfaces e modelagem de conceitos operacionais. O objetivo desta cerimônia é detalhar as Stories em uma perspectiva de objetos do produto e de seus componentes. Nela, devemos refinar o overall model com mais detalhes sobre os objetos constantes nas Stories, nos cenários de aceitação e nas regras de negócio. Ao fim desta cerimônia, também faremos a representação do funcionamento operacional do produto e de seus componentes usando UI Storyboards. Todos os atores do React participam desta cerimônia. Ela é composta... por três etapas. Modelagem funcional, modelagem de interfaces e modelagem de conceitos operacionais. Ao fim, os artefatos gerados são o overall model refinado, interfaces internas e externas e UI Storyboards. Na primeira etapa, nós realizamos a modelagem funcional. Nela, nós utilizamos o overall model encontrado durante a segunda etapa da Story Discover. Naquele momento, nós encontramos as classes e os seus colaboradores. Agora, chegou a hora de definir responsabilidades para cada uma dessas classes. Por responsabilidade, devemos entender dados e ações que são processados por essas classes. Assim, devemos voltar aos nossos CRC Cards e, com base na interpretação de cada classe e dos requisitos que lhes citamos anteriormente, iremos definir dados e processamentos realizados por essas classes sobre esses dados. Como exemplo, nós temos que a classe de dados é a classe de dados. Como exemplo, nós temos que a classe de dados é a classe de dados. A classe filme terá como dado uma ficha técnica, média de notas dos usuários, resenhas e comentários dos usuários. Já a classe legenda terá como dados idioma, cor e tamanho. Como exemplo de ação realizada por uma das classes, temos o cadastro, que gera um ID de usuário. Na segunda etapa, realizamos a modelagem de interfaces. Por interface, devemos entender a prestação de um serviço por algum sistema. Essas interfaces podem ser do tipo internas ou externas. As interfaces internas são pontos de comunicação entre diversos módulos ou componentes dentro do sistema. Elas definem como os diferentes elementos do sistema interagem entre si para realizar suas funções. Usando o Overall Model como exemplo, podemos ver que o processamento realizado por alguma daquelas classes constitui, como exemplo, um processo de análise. Uma interface que vai ser utilizada por uma outra classe, no caso, uma de suas colaboradoras. Já as interfaces externas são os pontos de comunicação entre o sistema e o ambiente externo, como outros sistemas, dispositivos ou usuários. Essas interfaces definem como o sistema recebe entrada do ambiente externo, processa esses dados e fornece saída de volta ao ambiente externo. Ao final, vamos ver como o sistema interagem entre os dois sistemas é realizado. Ao falar de interfaces externas, devemos lembrar de APIs e outras aplicações prestadas pela internet. Para encontrar essas interfaces, devemos analisar os componentes definidos no Overall Model, a fim de identificar, para cada classe, as interfaces que ela fornece e as informações destas interfaces, como tipo de interface , dados necessários de insumo que a interface solicita e o serviço de saída fornecido por essa interface. Essa identificação pode ser registrada também em cards sucintos, sendo que esses cards devem ter um título, a definição dos dados que recebe, a definição do serviço que fornece e sua identificação. Como exemplo de interfaces externas do nosso projeto de streaming, teríamos uma interface de integração com o Instagram para permitir o acesso à conta de usuário e fazer publicações, como Stories ou Posts. Outras interfaces seriam as de integração com a Receita Federal para fazer a validação do CPF do usuário no momento do cadastro, assim como há também uma interface de integração com os Correios para a validação do CEP do usuário. Já as interfaces internas devem ser encontradas a partir do Overall Model, suas classes e as colaborações entre elas. Por exemplo, na colaboração entre a classe Filme e o Cep, entre a classe Filme e Player de Vídeo, é possível concluir que há uma interface de exibição de filmes, onde o Input será a seleção de exibição de um filme do catálogo e o Output será a exibição do filme. Outro exemplo pode ser a colaboração entre filme e legenda. Nesse caso, o Input será a seleção de exibição da legenda em português ou outro idioma e o Output é a exibição da legenda no Player de Vídeo. É importante que os cards que contenham as interfaces identifiquem qual é o tipo delas e também, no caso das interfaces internas, é interessante colocar um código que identifique as classes que colaboram para a existência daquela interface. Por último, na terceira etapa, realizamos a modelagem de conceitos operacionais. Nesta etapa, o objetivo é criar representações do funcionamento do produto na visão do usuário. Para isso, a técnica de UI Storyboard é utilizada. A técnica consiste no uso de formas sistemáticas de storyboards como mockups de telas que simulam o fluxo operacional do produto. Primeiro, é preciso mapear o encadeamento das user stories de forma lógica, encontrando suas dependências e os fluxos de negócios subjacentes a elas. É possível criar também storyboards a partir de uma única story, como foi o nosso caso. No primeiro exemplo, a gente vai criar uma série de storyboards. No primeiro exemplo, nós temos um encadeamento de três user stories que formam o fluxo de um serviço prestado por um aplicativo de banco. Mas, no nosso caso, uma única story necessitou de mais de um storyboard para representar o fluxo de atividade contido naquela story. O exemplo que utilizamos é o carregamento de um filme para o catálogo do nosso streaming. E assim, todas as etapas são representadas em storyboards de alto nível. É preciso ressaltar que, neste momento, não há necessidade de se preocupar com a fidelidade e realidade desses storyboards. O principal objetivo aqui é mostrar o fluxo de atividade de uma funcionalidade. Esses storyboards, além de servirem como mais uma camada de validação pelo cliente e pelo domain expert, também podem ser utilizados para ajudar a equipe de desenvolvimento na fase de implementação do código. E assim, chegamos ao fim do último módulo do nosso curso, onde vimos como encontrar e modelar interfaces internas e externas da arquitetura do sistema e como criar protótipos com UI storyboards.
